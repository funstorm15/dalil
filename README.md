# DALIL — AML investigation copilot

**Partner product** · MKBANK Financial Crime Compliance (alert-investigation desk) · Central Bank of Uzbekistan AML/CFT context

> An analyst receives ~40 alerts a day. Each one is 30–40 minutes of scrolling transactions,
> transliterating UZ/RU counterparty names, and pattern-matching against typologies.
> **DALIL turns that into a 220-word, fully cited investigation note in ~20 seconds —
> on-premises, with the data never leaving the bank.**

**Live demo:** https://cornbread-left-licking.ngrok-free.dev · Repo: this page

---

## 1. The problem

- Transaction-monitoring systems emit **thousands of alerts/month**; L1/L2 analysts drown.
- Rules-only systems on messy UZS data have a **false-positive rate of ~57%**
  (measured on our held-out synthetic test set — see §5). Every FP costs an analyst ~30 min.
- Outsourcing narratives to a cloud LLM is a **compliance non-starter**: customer transaction
  data cannot leave the bank perimeter, and every claim in a SAR-ready note must be traceable
  to the underlying evidence.

## 2. What DALIL does

Paste a case CSV (or pick one from the demo queue) → DALIL returns, via a live stage-streamed UI:

1. **Risk score 0–100** — ensemble of a calibrated gradient-boosting model (70%) and a
   transparent scenario-rules layer (30%), banded low/medium/high/critical.
2. **Triggered typologies** — SC-01 structuring, SC-02 rapid pass-through, SC-03 mule fan-in,
   SC-04 gamed turnover, SC-05 crypto bridge, SC-06 cash-trade layering — each with hit evidence.
3. **Investigation narrative** — 4 sections (Summary / Typology / Key evidence / Next steps),
   generated by a **local open-weight LLM**, where every factual claim carries an `[E#]`
   citation into the evidence list.
4. **Citation verification** — an automated checker re-parses the note; unknown `[E#]` ids and
   unverified numbers are flagged in the UI before the analyst ever sees them
   (measured: **0 invalid citations** across the eval sample).
5. **Leave-one-out attribution** — which features pushed the score, with sign and magnitude.
6. **Immutable audit trail** — every decision, model version, and narrative mode logged.

**The data never leaves the machine.** The LLM is Qwen2.5-1.5B-Instruct (Apache-2.0) served by
llama.cpp on localhost — the same OpenAI-compatible interface a bank's on-prem vLLM/TGI would
expose, so production only changes `LLM_BASE_URL`. If the model is down, DALIL degrades to a
deterministic extractive narrative **and labels it as such** — never a silent fake.

## 3. Architecture

```
                 ┌────────────────────────── bank perimeter ──────────────────────────┐
  CSV / queue ──▶│ FastAPI                                                             │
                 │  ingest → entity clusters (UZ/RU translit) → 49 features            │
                 │       → scenario rules SC-01..06 ─┐                                │
                 │       → HistGB risk model ────────┤→ ensemble score (0.7·ML+0.3·R) │
                 │       → evidence pack ──▶ llama.cpp :8081 (Qwen2.5-1.5B, local)    │
                 │       → citation verifier → narrative + audit log                  │
                 │  SSE stage stream ──▶ React SPA (queue / investigate / system)      │
                 └─────────────────────────────────────────────────────────────────────┘
   zero egress at runtime · model + rules shipped in the image · audit JSONL on disk
```

- **Demo runs entirely inside one Docker image** (HF Space, 2 vCPU): API, SPA, local LLM.
- **Production shape**: same API next to the bank's DWH; swap the GGUF for an on-prem vLLM
  serving the same OpenAI-compatible route; retrain `scripts/train.py` on real labelled alerts.

## 4. Try it

Live deployment: **https://cornbread-left-licking.ngrok-free.dev** (demo tier — the stack runs on
the demo laptop and is exposed through an ngrok tunnel; first browser visit shows ngrok's
interstitial, click "Visit Site". Narratives take ~20–25 s on 2 CPU threads.)

Local:

```bash
make setup          # uv venv + pip + npm ci
make data model     # regenerate synthetic casebook + retrain (already committed)
make llm            # fetch llama.cpp + Qwen2.5-1.5B GGUF (~1 GB, Apache-2.0)
make llm-serve &    # local model on :8081
make serve          # app on :8000  → open http://localhost:8000
```

Without `make llm`, the app still works — narratives fall back to deterministic mode.

## 5. Results (honest numbers)

Full report: [`eval/results/eval_report.json`](eval/results/eval_report.json).
Synthetic data, so **ROC-AUC is optimistic — the operationally meaningful rows are marked ★**.

| Metric | Test (seen process) | Novel split ★ (unseen typology params) |
|---|---|---|
| Model ROC-AUC | 0.9945 | 0.9937 |
| Ensemble ROC-AUC | 0.9969 | 0.9963 |
| **Rules-only FPR** | **57.0%** | **58.1%** |
| Ensemble FPR @ band 50 | 2.0% | **0.4%** |
| Ensemble recall @ band 50 | 99.7% | 99.2% |
| Precision @ 10% real-world prevalence | 84.7% | **96.4%** |
| Rules-only recall | 91.7% | 79.1% (degrades on novel typologies) |

★ **The story the numbers tell**: rules fire on more than half of all clean cases
(cash-intensive trade, sub-threshold salary patterns) and still miss 21% of novel laundering.
The calibrated model cuts false positives ~14× while *raising* recall — that is the whole
business case, and it survives held-out typology parameters, not just a random split.

**Narrative quality** (shipped default 1.5B + few-shot, n=20 held-out cases): mean citation
precision **0.95** (fail-closed: zero-citation notes score 0), **0** invalid `[E#]` citations,
1 unverified number total (flagged in UI). The 3B option scores 1.0 on spot checks at ~2× latency.

**Failure analysis is in the report** (5 FPs: all clean SC-06 cash-trade near-misses;
1 FN: structuring case where ML ≈ 0.001 despite rules firing — shown in the System tab).
Per-typology recall: cycle-layering is hardest (rules 55–66%, ensemble mean score ~76).

**Latency**: pipeline (no LLM) p50 **108 ms** / p95 181 ms on a laptop; full narrative
**p50 25 s** (1.5B, 2 threads — deliberately conservative, matches the 2-vCPU Space;
~20 s on 8 threads).

## 8. Limitations (we do not hide these)

1. Synthetic ≠ production UZS flows; expect a few points of drift on real data. Re-training is
   one script + a JSONL swap.
2. No cross-case beneficial-ownership graph — clusters resolve within a single case only.
3. UZS-only generator; FX/hawala corridors out of scope.
4. The 1.5B narrative occasionally states a number the verifier can't tie to evidence (~15%);
   it is flagged, never silently trusted. The 3B option improves this at ~2× latency.
5. HF Space (2 vCPU) is a demo tier: ~20–40 s narratives; production targets GPU on-prem.
